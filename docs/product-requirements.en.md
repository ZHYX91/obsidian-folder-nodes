# Folder Nodes — Product requirements

## Product model

A complete Folder Node is a folder with exactly one same-named Node Note, `A/A.md`; its structural identity remains that current normalized pair. A managed folder or Markdown without its counterpart is an incomplete node that the user may complete or mark unmanaged. Root may have its optional Node Note at the Vault root. Folder Nodes writes no permanent ID, `_pkwf`, path, parent, name, node type, or complete child list.

## Sort properties

Natural name order writes no sort property. Manual order uses `folderNodeChildrenSort: manual` on the parent Node Note and a sparse positive `folderNodeSiblingRank` on each direct Child Node Note. A normal reorder writes only the moved node; local rebalance is bounded to 64 nodes. Missing or duplicate ranks use normalized basename and path as deterministic tie-breakers. Rename retains an existing rank, and a new child in manual mode appends by default.

## Node operations

Users can create, rename, move, merge, safely delete, and reorder complete nodes. Explorer and Contents child-node drag placement mean before, into, or after: same-parent placement reorders, and cross-parent placement reparents and reorders. Every structural write must be serialized, rename/move must use Obsidian FileManager, and multi-step writes must preflight and roll back on failure. Conflicts, cyclic moves, and ambiguous merges fail closed. Obsidian's native New folder and New note actions remain visible beside New node: the native actions create an incomplete folder or Markdown half, while New node creates the complete pair atomically. File Explorer folder move/delete acts on the whole subtree; a Node Note tab's move/delete/merge acts only on that Markdown file and may leave an incomplete folder. Rename is the synchronization exception: renaming either an existing Node Note or its folder updates the other half. Explicitly labelled containing-node actions handle whole-node intent from a Note tab. Root cannot be renamed, moved, or deleted as a complete node. Folder Nodes creates blank Node Notes; content templating belongs to dedicated template plugins.

## Selection creation

Editor commands and context menus create Child Nodes from selected text. Creation previews the final `A/A.md`, alias, and wikilink. On confirmation, the selected text becomes the new Node Note body and the original selection is replaced by the previewed wikilink; a changed selection or source file stops the write. A single Markdown table cell is supported in Source and Live Preview: the generated wikilink uses an escaped `\|` alias separator. A selection that crosses an unescaped cell boundary or table row fails closed before creating anything. In this flow, aliases use only selected visible text; prefixes, suffixes, independent separators, and timestamps affect only the basename. Sources are current file, current node, nearest current heading, timestamp, and custom text.

In managed scope, clicking an unresolved internal Markdown link creates the complete Node directly instead of first creating a leaf note. `[[a]]` creates a blank `a/a.md`; explicit Vault paths create every missing complete ancestor Node transactionally. When the shared aliases setting is enabled, `[[a|b]]` writes the explicit display text `b` to the new Node Note's `aliases`; without display text or with the setting disabled, it writes no alias. Unmanaged folders, unmanaged leaf-note paths, unsafe or non-Markdown targets, and links outside Markdown views remain under Obsidian's native behavior. External and third-party creation is never auto-converted; users may invoke Convert to Folder Node explicitly. Conflicts fail closed.

## Homepage and unmanaged boundaries

The Root Node Note is at the Vault root and uses the Vault name with illegal filename characters sanitized as its basename. Users may make it a homepage, open it by command or from Contents View, and optionally open it after Vault layout restoration. Contents resolves the current node from the active file's owning folder and falls back to Root when no file is active. File Explorer always exposes Root as a pinned, non-collapsible row distinct from ordinary nodes. General contains two unmanaged rule groups for Markdown files and folders, followed by optional bulk organization and read-only Health. Both rule groups accept exact Vault-relative paths and plain-language name-start rules, with `.` and `_` as defaults. Unmanaged rules stop node classification, bulk organization, and structural repair but do not hide content. The active Vault configuration folder, `.git`, and `.trash` are always protected; root `AGENTS.md` and `CLAUDE.md` are unmanaged Markdown paths by default.

## Node Visual and Contents View

`icon` is the only Node Visual property. It uses Obsidian-Properties-compatible Text or a flat Text List and never a nested object. Base candidates are Vault image wikilinks, known Lucide icons, or one visible extended grapheme (letter, symbol, or emoji). The first actually renderable base wins; a missing image continues to later local candidates. The first valid `color:` item colors Lucide/glyph foregrounds. Emoji, raster images, and SVG preserve their pixels without an added marker, background, or border; color becomes a centered solid circular swatch only when every base fails. Unknown or multi-grapheme entries are diagnosed and cannot be saved through the Picker; the first color wins. Nearest-ancestor inheritance begins only after the whole local declaration is exhausted and never combines a local color with an ancestor base. Property icons appear in a fixed frameless slot, with glyph weight, size, and color distinguishing them from identical characters at the start of a file name. File Explorer icons may appear before or after the name or remain hidden, and may also appear beside—but outside—the editable Node Note title. Glyphs inherit Obsidian's interface font. Emoji default to the platform color stack; Icons & appearance lists only detected families from the curated Segoe UI Emoji, Apple Color Emoji, Noto Color Emoji, Twemoji Mozilla, and OpenMoji set, shows a complex-sequence preview, and falls back safely when a saved family is unavailable. Advanced CSS variables remain available. File Explorer is the only global Node Tree and starts with the pinned Root row. The sidebar browses only direct contents through independently paged Nodes, static Album, and compact Files sections. All three entry types expose context-menu, More actions, and Shift+F10 access. Nodes reorder or reparent through before/into/after placement. One ordinary Album/Files item may move only into a node, the current node, or a breadcrumb folder and writes no order metadata. Content multi-selection inserts or copies wikilinks; dragging multiple selected items exports links and never performs a partial file move. Child nodes without a valid visual have no large fallback artwork. GIFs use a still frame, videos use a type tile, and audio stays in Files. The plugin provides no inline animation, video, or audio playback in the sidebar.

## Structural safety

Folder Nodes has no initialization or adoption state. Once enabled, it immediately classifies complete, incomplete, unmanaged, and conflicting structures, and automatic rename synchronization applies only to unambiguous complete pairs. Native creation never auto-completes or moves content. Missing folder and Markdown halves both use a neutral Incomplete node state with explicit complete and Set as unmanaged actions; only true pair conflicts use warnings. Optional bulk organization uses a cancellable batched read-only scan, lists every create, move, skip, and block path, revalidates before commit, validates afterward, and rolls back any failed step. Health is strictly read-only and has no write button. Complete-node deletion uses system trash. The plugin makes no network requests.

## v1 boundary

v1 excludes remote image fetching, inline SVG recoloring, automatic initials from node names, nested `icon` objects, PDF first-page thumbnails, HEIC/HEIF preview, video frame extraction, inline animation/video/audio playback, ordinary-file independent ordering, transactional multi-file moves or cross-view internal drops in Contents View, a second complete directory tree, alternate Node Note naming, complex merge-conflict UI, and arbitrary property inheritance.
